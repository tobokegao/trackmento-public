# 割り付け（書き出し画像の組み方）

マスと曲名リストをどう置くか。**`backend/render.py` と `frontend/index.html` の `renderShareCanvas` の二重実装**なので、
片方だけ直さない。突き合わせは `scripts/compare_layout.py`（数値）と `scripts/compare_render.py`（絵）。

（`CLAUDE.md` から分けたもの。2026-09-20。中身は当時のまま）

## マスの形（正方形 / 横長 16:9）（2026-09-21）

`CELL_PX = 600` を `CELL_W = 600`（固定）と `cell_h(doc)`（600 か 338）に分けた。
16:9 は 600×337.5 の小数を避けるための丸めで、実比は 16:9.01（誤差 0.15%）。

**幅を変えない**ので、幅から決まる式はそのまま効く。どの式が何を見るか:

| 何 | 見るもの | なぜ |
| --- | --- | --- |
| `gw`（塊の幅）、`_mod_pad` の `step`、タイトルの大きさ、サイドバーの幅 | **幅**（`CELL_W`） | 変わらない |
| `gh`（塊の高さ）、曲名リストの段の送り（`pitch`）、`_snap_lead` | **高さ**（`cell_h`） | 段はマスの高さで決まる |
| 帯や番号を出すかの判定（`overlay_ok`）、`WRAP_CELL_OK` の下限 | **短辺**（`cell_short`） | 幅で見ると 16:9 が実際より大きく見積もられ、潰れた帯が出る |

### ぼかし埋め

マスと比の違う絵が来たときの入れ方は 2 つ（**正方形のマスでも効く**。2026-09-21 までは正方形でないマスだけだった）。`options.cellFit`（`"crop"` 既定 /
`"blur"`）で決め、`Track.fit` でマスごとに上書きできる。**判定はしない**（下の「やらなかったこと」）。

**下地はマスより広く作ってから切り取る**（`blur_margin` = 半径の 3 倍）。マスちょうどで作ると
端に外側の色が無く、縁がにじんで四角の枠がぼやける。ブラウザの `blur()` は描画範囲の外を
透明として扱うのでなおさら目立つ。

実測（3x3・16:9・正方形ジャケット 9 枚・出力 2400px、2026-09-21）:

| | 6px のぼかし後 | グリッド側 |
| --- | --- | --- |
| 広げる前 | 1.57% | 2.21% |
| 広げた後 | **0.09%** | **0.07%** |

にじみ方の違いが差の主因だった。

### やらなかったこと: 文字のあるジャケットの自動判定

「文字が目立つなら埋め、目立たなければ切る」を自動でやろうとしたが、**精度が出ない**。
切り落とされる帯のエッジの細かさで測ると、みんなの並びの iTunes ジャケット 24 枚で
0.005〜0.304 に分かれたものの、**高スコアは文字ではなく絵の細部**（葉・花・装飾）で、
**文字のあるジャケットが 0.005**（細い文字が 64×64 への縮小で消える）だった。
解像度を上げると今度は写真の細部を文字と誤認する。

さらに、サーバー（PIL）とブラウザ（Canvas）で判定が 1 件でも食い違うと、同じ並びが
別の絵になる。**利用者がマスごとに選ぶ**形にした。

### マスが大きい並びの差（既存の性質）

3x3 のようにマスが大きい並びは、**画像のリサイズ品質の差**（PIL の LANCZOS と Canvas の補間）で
グリッド側に 2% 前後の差が出る。正方形でも 16:9 でも同じで、**割り付けは合っている**
（曲名リスト側は 0.00〜0.11%）。`compare_render.py` の基準「6px で 0.3% 未満」は文字と位置の
ずれを見るためのもので、絵そのものの差は別に見る。

## 曲名の刈り込みは割り付けの前（2026-09-21）

曲名とアーティスト名から蛇足を外す（`backend/names.py` と frontend の `trimName`）。
**割り付けを決める前に通す**。`layout()` と `render()` の入口で `_trimmed(doc)` を呼び、
ブラウザ側は `layout()` と `renderShareCanvas` が `viewCells()` を読む。

あとから刈っても意味がない。`_wrap_plan` は「出力での文字を `FLOW_MIN_FONT` に固定し、入る枠を
いちばん小さくする」で決まるので、**文字を減らさないと枠が縮まない**。

`layout()` と `render()` の両方で刈るので**二重に掛かる**。`names.trim` は掛け直しても結果が
変わらない（`scripts/check_trim.py` が確かめる。みんなの並び 882 曲で差 0 件）。

実測（利用者の 100 曲・10x10・16:9・出力 2000px）:

| | 文字数 | 1 マス | 塊の面積比 | 組み方 |
| --- | --- | --- | --- | --- |
| 刈り前 | 5,421 字 | 64px | 18.5% | 回り込み |
| 刈り後 | 3,859 字 | 102px | 46.5% | 流し込み（右） |

突き合わせは `scripts/check_trim.py`（期待値の表と冪等性）と `scripts/compare_trim.py`
（Python と Chromium の全件一致）。10x10・16:9・全マス埋めの絵は**差 0.00%**（2026-09-21）。

`scripts/compare_layout.py` は **200 通りで 0 件**（2026-09-21）。

### 突き合わせの前にサーバーを立て直す（2026-09-21）

`frontend/index.html` を直したあと、**サーバーを立てたまま**突き合わせると、ブラウザ側が
**古い JS を読んで 25/120 食い違った**。`scripts/build_app.py` を回すと殻（`frontend/dist/index.html`）が
新しい `app.<hash>.js` を指すが、それを `scripts/upload_app_r2.py` で R2 に上げるまでは取りに行けない。

**画面側を直したら、突き合わせの前に `build_app.py` → `upload_app_r2.py` を済ませ、サーバーを立て直す。**
食い違いが急に増えたときは、まず配られている JS を疑う（`curl http://127.0.0.1:8000/ | wc -c` が
33 KB 前後なら殻、440 KB 前後なら 1 枚配信）。

- 描画は 2 系統: Web は端末の Canvas で描いて `/share/upload` に送る（`frontend/index.html` の `renderShareCanvas`）。サーバー描画（`backend/render.py`）は CLI と、描けない端末のフォールバック（`/share`）。レイアウト・色・文字の省略規則は両方同じ式。**片方変更時は他方も変更**し、`scripts/compare_render.py` で両方の描画を突き合わせる（差は輪郭のみが正常）。
  手順はスクリプトの docstring。サーバーは `PUBLIC_MODE=1 SHARE_BUDGET_GB=0 SHARE_LIMIT_PER_DAY=0 SHARE_LIMIT_PER_IP_DAY=0` で立てる（R2 が無料枠を超えていると 507、本番の共有数を復元して 1 日上限にも当たる）。
  **見るのは「ぼかし後の差 > 32」**。輪郭のズレはぼかすと消え、マスや文字の位置のズレだけが残る。
  **3px のぼかしで 1% 未満、または 6px で 0.3% 未満**なら正常。マスが少ないと文字が大きく、3px では
  輪郭が消えきらない（2026-09-14 の実測で 4x4 が 1.65%。6px まで掛けると 0.15%、行の位置は完全に一致）。
  16x16 は 0.06%、12x20 は 0.15%、8x8（流し込み）は 0.66%。
  **テスト共有は必ず `clean` で R2 から消す**。
  **絵ではなく割り付けの数値をまとめて比べるなら `scripts/compare_layout.py`**（`PYTHONUTF8=1
  .venv/Scripts/python scripts/compare_layout.py 260`）。並び × 比率を数百件回して、枠・縮尺・
  文字の大きさ・行数・塊の位置を突き合わせる。`compare_render.py` は 1 件ずつなので、
  割り付けの規則を変えたときはこちらで面を見てから、気になるものを絵で確かめるとよい。
  **曲の中身を両方にそろえること**（曲名の長さで折り返しの行数が変わり、そこから文字の大きさが決まる。
  画面側は手元のグリッドを読むので、そのままだと別物を比べることになる）。
  今の食い違いは 260 件中 7 件で、すべて 1 曲 1 行のときの枠の幅が 1px 違うだけ
  （`_title_width` の PIL と Canvas の計測差）。
  ブラウザ描画の共有は `node promo/browser_share.mjs <サーバーの ID>` で拡張機能なしに作れる。
  割り付けの値そのものを見るなら `node promo/dump_layout.mjs <ID>`（frontend の `window.__layout` を呼ぶ）と
  `backend.render.layout()` を並べる。字幅の食い違いを疑うときは `node promo/dump_widths.mjs <作業用ディレクトリ> <ID>`。
  共有ページの見た目は `node promo/shot_share.mjs <ID> <出力.png>`
- **割り付けの総点検**: `PYTHONUTF8=1 PUBLIC_MODE=1 .venv/Scripts/python scripts/layout_audit.py --render`。
  並び（横×縦、1 辺 32・総数 256 まで）と比率 5 種の**全 2,950 通り**を組んでみて、
  出力での曲名・タイトル・マスの大きさ、文字の埋まり具合、段の狭さを数値にする。
  しきい値に引っかかったものだけ画像にして `outputs/layout-audit/index.html` にまとめる
  （`outputs/` は git 管理外）。`--from-json` で測り直さずに HTML だけ作り直せる。
  結果を外から見られる 1 枚の HTML（問題の種類ごとにひどい順 30 件の画像＋全件の表）にまとめるのは
  `scripts/layout_audit_page.py <出力先>`。
  **割り付けの規則を変えたらこれを回す**（1 つの組み合わせを直すと別の組み合わせが壊れることがある）

- **マスの番号バッジは、枠の寸法を字の大きさから決める**。字は 8px を下限にしている（ピクセルフォントは
  それ以下で潰れる）のに、枠だけ `sc(40)` で縮み続けていたため、16x16 では字 8px に対して枠 5px になり
  **数字が枠からはみ出していた**（2026-09-15 に利用者の出力で発覚）。`render.py` と `renderShareCanvas` の両方

- **柱・帯（塊を枠の辺にぴったり付ける組み方）**（`render.py` の `_slab_plan` と frontend の `slabPlan`、2026-09-15）。
  塊の縦横比と枠の縦横比が `SLAB_ASPECT`（4 倍）以上食い違うときだけ使う
  - **柱** … 1×y のように枠のほうがずっと横長のとき。塊を左端に立て、上下も枠いっぱいに伸ばし、
    右の 1 本の段にタイトル → 曲名リストを置く
  - **帯** … 32×y のように塊のほうがずっと横長のとき。タイトルを上端に、その下に枠の横いっぱいの塊、
    さらにその下に曲名リストを置く
  - **塊が片方の辺を使い切るので枠の大きさが一意に決まる**。回り込みのような二分探索が要らず、
    決めるのは文字の大きさだけ（`SLAB_TARGET_PX` を大きいほうから試して、入る中のいちばん大きいもの）
  - 切り替えは「マスが **`SLAB_CELL_GAIN`（1.02）倍以上**大きくなる」か
    「マスが同じでも**文字の置き場所を `SLAB_USE_MIN`（0.7）以上使えている**」とき。
    **2 つ目の条件が無いと空白が増える**: 曲が少ないうえに塊が細長い並び（11x1 を 9:16 など）だと、
    比率で決まる縦長の枠に対して曲名リストが短く、下に大きな空白が残ったまま辺に付いてしまう
    （実測で埋まり 0.6 → 0.35 に落ちた）。1% ほどのマスの差で選ばせてもいけない
  - 実測（出力でのマス）: 31x7 9:16 が 36 → 39px（左右ぴったり）、1x8 1:1 が 213 → 273px、
    1x32 16:9 が 23 → 38px。全 2950 通りでマスが小さくなったのは 1 件だけ
  - タイトルは本文の `SLAB_TITLE_SCALE`（2.4）倍。回り込みの 4.0 倍だと 32x1 で出力 192px になり
    「大きすぎる」と指摘があった
  - **タイトルは枠の上端いっぱい**に置く（利用者の指定）。ただし**柱では帯のぶん枠が縦に伸び、
    そのままマスが小さくなる**（塊の高さは決まっているため）。頭打ちが無いと 1x8 を 1:1 で
    273 → 213px まで落ちるので、帯は塊の高さの `SLAB_TITLE_BAND`（10%）までにしてある
  - **1〜3 列の並びでは、曲名をマスの横に、マスと同じ並び順で置く**（`_slab_rows` / `slabRows`）。
    **マスの段 1 つぶんの高さに、その段のマスと同じ数だけ曲名を積む**（3 列なら 1・2・3 曲目、
    4・5・6 曲目、…）。どのジャケットがどの曲かが目で追える。1 曲ぶんの高さは
    「マスの段の送り ÷ 列数」で、番号 → 曲名 → その下にアーティスト名。
    **4 列以上には広げない**（`SLAB_ROW_MAX_COLS`）。1 曲ぶんが薄くなりすぎて文字が読めない
    枠も曲名の大きさも探索が要らない（枠は塊とタイトルの帯だけ、曲名はマスの送りの
    `SLAB_ROW_FONT`＝30% で決まる）。**マスが小さいと 1 曲ぶんの高さも足りなくなる**ので、
    出力での曲名が `SLAB_ROW_MIN`（= FLOW_MIN_FONT、20px）を下回るなら流し込みに戻す。
    だいたい 1x20 が境目（1x8 1:1 で本文 74px、1x20 1:1 で 31px、1x32 16:9 は 12px なので流し込み）
  - **切り替えの条件**: 比率なしは無条件、比率ありは「流し込みに落ちる」か「マスが今の組み方より
    小さくならない」とき。実測で 2x5 1:1 が 338 → 390px、2x6 1:1 が 284 → 325px、3x6 1:1 が 334px
  - **比率なしの段の幅は `SLAB_ROW_SEG`（30 字ぶん）と「塊の高さの `SLAB_ROW_WIDE`（75%）」の小さいほう**。
    比率が無いと枠から残りを逆算できないので字数で決めるが、**上限が無いと段のほうが塊より長くなり、
    枠が横に伸びてマスが潰れる**（1x3 free で 600 → 223px、2x4 free で 543 → 365px になっていた）。
    75% にすると 2x4 free が 433px、3x3 free は元の 375px より大きい 422px になる
  - **「マスごと」は割り付けの総点検で埋まりを測らない**（`layout_audit.py`）。1 曲 1 行と同じで
    曲の数ぶんの行しか無いのが正しい姿で、まわりの空きは欠陥ではない。
    測ってしまうと 1x8 1:1 が「埋まり 56%」で要確認に挙がる
- **曲名の回り込み**（`render.py` の `_wrap_plan` と frontend の `wrapPlan`、2026-09-15）。
  曲が多くて流し込みに切り替わり、かつ比率が決まっているときの組み方。
  **マスの塊を枠の中央に置き、まわりの余白に曲名を流し込む**
  - それまでは「上にマス・下に曲名」で組んでいた。内容が縦長なので比率合わせで**左右にごっそり
    余白が残り**、そのぶんマスが小さくなっていた（16x16・1:1 の実測でマスの塊が枠の 44%）。
    まわりに流せば余白を使い切れるので、同じ出力サイズでマスが大きくなる（**44% → 56%**）
  - **切り替えるかどうかは実際に組んでみて決める**（`layout()` の最後）。
    「マスが小さくならない」（`wp.scale >= scale`）か、「今の組み方では文字が `WRAP_SWITCH_PX`（12px）未満で
    まったく読めない」かのどちらかのときだけ回り込みにする。**無条件に切り替えてはいけない**:
    9:16 に正方形の並びを入れると、塊を中央に置くぶんマスが小さくなるだけで得が無い
    （実測 16x16・9:16 でマス 62px → 39px）
  - 枠の大きさは「**出力での文字を決め打ちし、入る範囲で枠をいちばん小さくする**」で決める
    （枠が小さいほど、出力に占めるマスの塊が大きい）。塊に対する % を二分探索する。
    - 文字は `WRAP_TARGET_PX`（20 → 18 → 16 → 14 → 12px）を上から試し、**入る中でいちばん大きいもの**。
      曲が多くて横長（21x12 を 16:9）だと 20px ではどう組んでも入らない
      （2400x1350 に 30px 行間で 45 行しか置けない）。そこだけ落とす
    - `WRAP_GRID_MAX`（0.72）で塊が枠の 72% を超えない大きさから探し始める。
      **これが無いと塊が大きくなりすぎて、左右が数文字ぶんの細い隙間になる**
    - `WRAP_GRID_MIN`（0.45）を下回るほど枠を広げない。当たったら次の（小さい）文字で探し直す。
      **文字を優先しすぎるとジャケットが豆粒になる**（21x12・16:9 で塊が枠の 30% になっていた）
    - 入る大きさが見つかったら、**余地があるぶん文字を大きくし直す**（`WRAP_TARGET_UP`）。
      大きくすると枠も少し大きく（＝マスが少し小さく）なるので、**最初に見つけた大きさのマスから
      `WRAP_CELL_KEEP`（0.90）を割ったら止める**。1 段ずつ前と比べると少しずつ縮んで歯止めが効かない。
      これで下の帯まで文字が埋まる（全組み合わせで埋まり具合の中央値 1.00・最小 0.60）
  - **左右に段が作れないときは、塊を上に寄せて文字を全部下に流す**（2026-09-16）。
    上下の帯だけになると「01〜13 が上・14〜20 が下」で読み順が塊をまたいで飛ぶ
    （利用者から 5x4・1:1・20 曲の出力で指摘）。**枠の大きさも文字の総量も変わらないので
    マスの大きさはそのまま**（実測 427px → 427px）。「タイトル → マス → 曲名リスト」になる。
    左右のどちらかが使えるときは今までどおり（コの字・回り込み）
    - 縦積みの組み方（回り込みをやめる）に切り替えるのとは**別物**。あちらはマスが
      半分近くまで小さくなる（5x4 1:1 で 427 → 233px、4x5 4:5 で 332 → 189px）
    - **このとき文字の幅は塊の幅にそろえる**（2026-09-17）。枠のほうが塊より広いと（9:16 に 7x10 など、
      高さで枠が決まる並び）、文字だけ左右にはみ出して「マスと幅が合っていない」見た目になっていた
      （利用者の 7x10・9:16・70 曲で指摘）。`build` の `x0, x1 = gx, gx + gw`
      **代償**: 文字の幅が狭まるぶん行が増え、曲名の長い並びでは字が小さくなる（fav25 の 7x10・9:16 で
      本文 24 → 17px、マスは 127 → 169px）。利用者の並び（曲名が短い）では 4% 狭まるだけ。
      総点検は 33 → 34 件（増えた 3x7・9:16 は「埋まり 52%」＝文字の左右の空きを数えたもので、見た目は整っている）
  - 読む順は**上の帯 → 左の段をぜんぶ → 右の段をぜんぶ → 下の帯**。新聞の段組みと同じ。
    1 行ごとに左右へ飛ぶ組み方も試したが、**実際に読むと追えない**（利用者の指摘で直した）
  - **段の幅は `WRAP_MIN_SEG`（文字 20 字ぶん）を下回ったら使わない**。8 字ぶんで流していたときは
    曲名が数文字ごとに折れて読めなかった（実測で 8x12・9:16 の左右が 8 字ぶん）。
    上げてもマスはほとんど小さくならない
  - **左右が両方とも半端なら、塊を左端に寄せて右に 1 本の広い段を作る**（コの字）。
    中央に置くと 2 つとも「狭くて使えない」幅になって捨てになる。片側に寄せれば 2 つぶんが
    1 本にまとまり、文字の並びがちょうど「コ」の形になる（上の帯 → 右の段 → 下の帯）。
    実測で回り込みになる組み合わせの 3 分の 1 強がこれになる
  - **塊のまわりの余白は四辺そろえる**。行は「箱」で字面はその中央にあるので、行を等間隔に並べただけだと

    - **サーバー描画（`/share`）の大きさは上げない**。サーバーの CPU を使わないのがこの作りの前提なので、
      上げるとしたらブラウザ側だけ。そのぶん「ブラウザ描画とサーバー描画で組み方が違う」並びは増えるが、
      サーバー描画に落ちるのは Canvas が使えない端末だけ（`FLOW_KEEP_FONT` を下げたぶんは両方に効く）

## 曲名リストの流し込み（`_flow_rows` / `flowRows`）

CLAUDE.md の「二重実装の一覧」から移した（2026-09-24、プロンプト点検）。

**折り返しは字の単位。ただし両端をそろえること**がずれを抑える鍵。
字で折ると PIL と Canvas のわずかな計測差で折り返す位置が変わるが、行ごとに右端でそろえていれば
そこで吸収され、次の行へ積み上がらない（`compare_render.py` のぼかし後の差: 両端そろえ無し 3.19% →
**両端そろえ有り 0.71%**。基準は 1%）。曲の単位で折れば 0.05% まで下がるが、
行の頭がいつも番号になって規則的に見えるので採らなかった
- **語の尻尾だけが次の行へこぼれるなら、語ごと次の行へ送る**（`FLOW_TAIL` = 2 字・`FLOW_WORD_MAX` = 12 字、`tail_back` / `tailBack`、
  2026-09-20、利用者の 11x11・16:9・121 曲で「ビリー・アイリッシ／ュ」「La／ur」）。語の区切りは空白と記号（`FLOW_WORD_SEP`）。
  送った行の末尾の空白は外す。**曲名の最初の語は送らない**（番号だけが行末に取り残される）。こぼれるのが 3 字以上なら今までどおり字の途中で折る
- 余りの配分は**空白 1 つぶんまで**。上限を付けないと、1 行の曲数が少ないときに切れ目が間延びする
- **曲の切れ目（全角空白 1 つぶん）は必ず描く**。幅だけ取って描かないでいると、余りの無い行で
  曲と曲がくっつく（利用者の画像で「Chevon06 例え話」のように番号が前の曲名に貼り付いていた。
  2026-09-14 に直した）。行末に来た切れ目は数に入れない（使っていない送りを幅に含めると余りの配分がずれる）
- **折り返しの判定は字幅を 1px に丸めてから行う**。PIL と Canvas の字幅は 1px 未満だけ違い、
  生の値で足すと境目の字で折る・折らないが入れ替わって、そこから先の行が全部ずれる
  （丸める前 2.28% → 丸めた後 0.66%）。描くときは実寸のまま
- **ブラウザ側の字幅の控え（`CHAR_W`）は、Web フォントが効く前の値を持ち越してはいけない**。
  読み込み直後の `layout()` はまだ代替フォントで測るので、そのまま残すと**折り返しが
  サーバーとずれる**（16x16・16:9 の突き合わせで 0.26% → 3.69% になっていた。
  `renderShareCanvas` の先頭で捨て、`document.fonts` の `loadingdone` でも捨てる）
- **行の中身は 1 本のベースラインに乗せる**（`BASELINE` = 0.38。字の大きさに対する比）。
  PIL の `anchor="lm"` と Canvas の `textBaseline="middle"` は基準が違い、**文字が大きいほど
  食い違う**（出力 64px で 10px ずれた）。**字面を実測して決めてはいけない**:
  PIL の `getbbox` と Canvas の `actualBoundingBox` も数 px 違うので、固定比のほうが揃う
- **1px に丸める前に 1/64 px にそろえる**（frontend の `snapW`）。PIL は字幅を 1/64 px の固定小数で返すので、
  実寸がちょうど .5 px になる字（IBM Plex の `e` / `r` / `-`）だけ Canvas の実数と丸めの向きが食い違い、
  その 1 字から先の折り返しが全部ずれる。**190 字中 3 字の差で、回り込みの突き合わせが
  6px のぼかしで 0.94% → 0.07% まで変わった**
