# 共有（送信・保存・探す）

ブラウザで描いた画像の送信、保存、できあがりの見せ方、リンクカード、みんなのグリッド（/find）。

（`CLAUDE.md` から分けたもの。2026-09-20。中身は当時のまま）

- **共有画像の送信は「進み具合」を出す**（`openUpload` / `postUpload`、2026-09-16）。
  上りの細い端末では **1MB の送信に 81 秒**かかることがある（点検の実測。端末の CPU ではなく回線。
  描画と JPEG 化は送信の前に終わっているので、サーバーが測る時間は**本文を受け取る時間**そのもの）。
  何も出ていないと「固まった」と思って押し直され、**同じ 1MB がもう一度流れる**
  - `fetch` では上りの進みが取れないので、この経路だけ `XMLHttpRequest`（`upload.onprogress`）
  - **時間切れは「全体」ではなく「止まったら」で測る**（2026-09-16）。全体を短くすると、
    **成功するはずの送信まで切る**（点検で受け取りに 94.6 秒・122.7 秒かかった例が実在する。
    回線が細いだけで放っておけば通る）。「固まった」と感じるのは進みが止まったときなので、
    そちらを短く切る: 送信中は `UPLOAD_STALL`（45 秒）進みが来なければ、送り終えたあとは
    `UPLOAD_WAIT`（60 秒）返事が来なければ `abort`。全体の `UPLOAD_TIMEOUT`（3 分）は保険
    （**当時の値。2026-09-19 に 150 秒 / 300 秒へ延ばした。下の項を見る**）
  - **自分で切ったのか「やめる」を押されたのかで、そのあとの動きが変わる**。前者は
    `sendFailed` を立ててサーバー描画へ、後者は `aborted` でそこで終わり（押したのに
    裏で描き始めたら、やめた意味が無い）
  - 100% になったら「サーバーで保存しています…」に変える（そこから先は R2 への書き込み待ち）
  - 待っているあいだに**作者の曲を 1 つ**出す（`OWN_TRACKS`。題と URL だけで、宣伝文は書かない）。
    リンクには `?from=trackmento-upload` を付けてあるので、流入の印として数えられる
- **送り終えたあと（100%）の待ちは 150 秒**（`UPLOAD_WAIT`、全体 `UPLOAD_TIMEOUT` 300 秒、2026-09-19）。スマホのブラウザは
  まだ回線を流れている途中でも 100% と数えるので、60 秒で切っていたときは点検で 4 時間に 8 件（`[client]` の `up_wait`）が
  打ち切られてサーバー描画に回っていた。100% のあとは「やめる」を勧める文も出さない（「やめる」が 4 時間で 18 件押されていた）。
  サーバー側は `[upload]` 行で受け取りと保存の時間を分けて出す（`_note_upload`、点検の「共有の送信の内訳」）
- **「画像を保存」も手元の画像を渡す**（2026-09-16）。サーバーから落とし直す形だと、
  電波の悪いところで保存に失敗する（利用者から「画像保存がどうしても上手くいかない」と報告）。
  ブラウザで描いたときは同じバイト列が手元にあるので、`URL.createObjectURL` のまま `download` に渡す。
  **保存されるバイト列は同じ**（実測 2400x1350 の JPEG・400KB）。サーバー描画に落ちたときだけ
  今までどおりバックエンド経由（別オリジンだと `download` 属性が効かないため）
- **出来上がりのプレビューは手元の画像をそのまま見せる**（2026-09-16）。ブラウザで描いた場合は
  そのバイト列が手元にあるので `URL.createObjectURL` で出す。**今までは上げたものを R2 から
  読み直していて、作ったばかりの数百 KB をもう一度落としていた**（利用者の待ち時間そのもの）。
  「画像を保存」は今までどおりサーバーの原本（`/shares/<id>.jpg`）を指すので、保存される画質は変わらない。
  サーバー描画に落ちたときは手元に無いので、従来どおり URL を指す
- **出来上がりは 1 つの窓（`.pane-output`）**。共有したあとオプションを直して作り直したいとき、
  画像のぶんだけスクロールすることになっていた（スマホで報告）。窓にすればタイトルバーの「−」で畳める
- **送信中に出す「作者の曲」は `scripts/build_own_tracks.py` が作る**（125 曲）。Bandcamp の
  `tbkgao.bandcamp.com/music` から **Tobokegao 名義だけ**を拾い、作品ごとにページを開いて曲単位にばらす。
  題は「日本語 (English)」なら日本語のほうだけにし、ローマ字だけのものはスクリプトの `JA` 表で読み替える。
  **実行時に取りに行かない**（CSP が Bandcamp への接続を許していないし、送信中に外部を待たせたくない）。
  曲名は文言ではなくデータなので、`check_i18n.py` は `OWN_TRACKS` を見ない
- **カード用の画像（OG）はブラウザから送らない**（2026-09-16）。本体だけ送って、`share.store` が
  `og is None` のときに本体から作る（実測 57ms）。**送るバイトが 2 割減る**（本体 501KB ＋ カード 127KB
  → 本体だけ）。上りの細い端末の待ち時間がそのぶん縮み、ブラウザ側も 1 枚描かずに済む
  - **開いたままの古いタブは今までどおり送ってくる**ので、来たら今までどおりそれを使う
    （`check_uploaded` の `og` は省略可、`main.py` は `isinstance` で見る）。
    **ここを必須のままにすると、古いタブからの共有が全部 400 になる**
  - 背景色は `_bg_rgb(doc.options)` にまとめた（サーバー描画の経路と同じ式を 2 か所に書かない）
  - カードは 1200×630 に縮めるので、本体が一度 JPEG になっていても見分けはつかない
- **JPEG の品質は 0.78、指で触る端末の最大辺は 2000px**（2026-09-19。`shareMaxSide` と `share.JPEG_QUALITY`）。
  点検で共有画像の送信が 5% 以上 20 秒超・最長 155 秒・「やめる」3 件だった（遅いのは端末の上り）。実測 465KB → 327KB（-30%）。
  以前の記録: **JPEG の品質は 0.82**（ブラウザ・サーバーとも。2026-09-16 に 0.9 から下げた）。
  実測で 2400x1350 の出力が 501KB → 413KB（-17%）。見分けはつきにくく、X は投稿時に再圧縮する
- **「みんなのグリッドを探す」（`/find`）**（`backend/shareindex.py`、2026-09-16）。曲名・アーティスト名で、
  その曲が入っている共有を探せる。**載るのは共有するときにチェックを入れたものだけ**（`GridDoc.listed`、既定オフ）
  - **共有は本来「URL を知っている人だけが見られる」もの**。全部を探せるようにすると、他人の並びが
    黙って公開物に変わる。だから opt-in にしてある。チェックの無い共有は 1 件も載らない
  - **索引の実体は R2 の `listed/<id>.json`**（1 共有 1 ファイル、数百バイト）。`cache.sqlite3` は
    デプロイのたびにコンテナごと消えるので、覚えておく場所にできない
  - **1 つのファイルにまとめない**。R2 に追記は無いので、まとめると「読んで足して書き戻す」になり、
    同時に共有した人の分が消える。1 件 1 ファイルなら書き込みが競合しない
  - 起動後に `listed/` を一覧してメモリに載せる（`_seed_listed_index`。`imgcache/` の索引と同じやり方）。
    探すのはメモリの中だけで、SQLite も外部の検索エンジンも使わない
  - **作った日で切る**（`_alive_after`）。長く動いているプロセスでは索引だけがメモリに残るので、
    保持日数より古いものは出さない（開いても「見つかりません」になるため）。
    `scripts/r2_prune.py` は `listed/` を特別扱いしないので、実体も共有本体と同じ日数で消える
  - 突き合わせは NFKC ＋ casefold ＋ 空白落とし（`_norm`）の部分一致。空白区切りの語は **AND**
  - ページは `share.find_html`。**JavaScript を使わない**（フォームの GET だけ）で、共有ページと同じ CSS。
    `noindex` は付けたまま（載せた人が同意したのは「このサイトの中で探せること」）
  - **探す前の画面は「いろんな切り口」（`shareindex.varied`、8 件）→「最近のグリッド」（`newest`、12 件）の 2 節**（2026-09-24、open-use ⑤）。
    載る並び 899 件の大半が「私を構成する 9 曲」で、新しい順だけだとほかのテーマが埋もれていた。
    題に「構成する／した／して」（英語は make me / made me）を含むものを外し、同じ題（数字を除いて `_norm`）は新しい 1 件にまとめる。
    **言い回しだけ違う題もまとめる**（`_same_theme`、2026-09-24）。数字と記号を落とした形で、いちばん長い共通の部分が短いほうの 6 割以上なら同じ題。
    本番の点検で「好きな音MAD9選」「我的音mad9選」「9個の音MAD」が 8 件のうち 3 件を占めていたため。
    6 割は「好きな曲（VTuber）」と「好きな曲（アニメ）」を別に残す線（共通の「好きな曲」は 4/7）。共通が 1 字だけのときはまとめない（「赤」と「赤い曲」）
    運営が手で選ぶ形は採らなかった（毎回手間がかかる。利用者の判断）。「最近」からは「いろんな切り口」に出したものを除く
  - JSON は `/find.json`。探す前は `varied` も返す。**`/shares/{fname}` と経路がぶつかる**ので `/shares/search` にはできない
- **自分の共有をあとから外す・消す**（2026-09-26、利用者の求め）。登録なしで「共有した本人」を見分けるため、
  `share.store` が共有のたびに**鍵**（`secrets.token_urlsafe(18)`、144 ビット）を作り、**鍵そのものは返事の `ownerKey` で共有した端末にだけ**渡す。
  並びの JSON（`<id>.json`。誰でも読める）には `ownerKeyHash`（SHA-256）だけを置く。端末は localStorage の `trackmento:shareKeys`
  に `{id: {k, at, l}}` で覚え、書くときに保存期限＋1 日を過ぎたものを捨てる
  - 経路は `POST /s/<id>/unlist`（`listed/<id>.json` を消し、並びの JSON の `listed` を false に書き直す。共有 URL は生きたまま）と
    `POST /s/<id>/delete`（`scripts/delete_share.py` と同じ 4 つ＋控え。**アップロード画像は残す**）。本文は `{"key": …}`。
    鍵違い・鍵の無い古い共有は 403、無い共有は 404。端末ごとに 1 時間 30 回まで（`_check_owner_tries`）
  - ボタンは 3 か所: 「できあがり」の窓（`#unlist-btn` は載せたときだけ、`#share-del-btn` は確認窓を挟む）、共有ページ（`#own` の囲み。
    消すときはもう一度押してもらう。ブラウザの confirm は使わない）、探すページ（自分の並びの横に **Mac OS 8 のクローズボックス**＝中が空の小さな立体の四角。HIG の窓の図に × は無い。× を四角で囲むと目立ちすぎた。2026-09-26、利用者の選択）
  - 共有ページと探すページのボタンは `share._owner_script` の小さなスクリプトが出す（CSP の nonce を `page_html` / `find_html` に渡す）。
    **鍵の無い端末では何も出ない**。消した画像は img.trackmento.com（Cloudflare）のキャッシュにしばらく残ることがある
  - **2026-09-26 より前の共有には鍵が無い**ので、外すことも消すこともできない（従来どおり問い合わせ → `scripts/delete_share.py`）
- **曲ごとのメモ**（`Track.note`、2026-09-22、利用者の求め）。マスを選んだときの編集欄に書く「選んだ理由」などを、
  共有ページ（`share.page_html`）の曲名リストで曲名の下に出す
  - **書き出す画像には描かない**。画像に入れると `render.py` と `renderShareCanvas` の割り付けを両方作り直すことになり、
    二重実装が大きく増えるため（利用者も画像には要らないと判断）
  - **「みんなのグリッドを探す」の索引には入れない**（`shareindex` が拾うのは曲名とアーティスト名だけのまま）
  - 200 字・3 行まで（`models.MAX_NOTE` / `MAX_NOTE_LINES`）。行ごとに空白を詰め、空行は落とし、何も残らなければ `None`。
    ブラウザ側は 3 行を超えた分を切るだけで、整えるのはサーバー
  - 出すときは `html.escape` して、改行は CSS の `white-space: pre-line` で残す（`<br>` を組み立てない）。
    リンクの `<a>` の外に置くので、メモを押しても元のページには飛ばない
  - 利用者が書いた自由な文が trackmento.com の上に出るので、プライバシーポリシーの「共有画像および共有ページ」にメモを書き足した
  - 荒らしや削除の依頼が来たときの消し方は `docs/ops.md` の「共有を期限より前に消す」（`scripts/delete_share.py`）
