# R2のClass A操作を減らす（全件一覧の間引きと起動時の相乗り）

2026-09-20

## 何を直すか

R2のClass A操作が無料枠（100万回/月）を超えている。原因の大半は、共有の容量上限を測るためだけに
10分ごとに回している**バケット全件の一覧**。

### 実測（2026-09-20）

バケットは211,301件・30.41 GB。全件の一覧に132秒、Class Aで212回かかる。

| 内訳 | 件数 | 容量 |
| --- | --- | --- |
| 共有（バケット直下の `<id>.jpg` / `-og.jpg` / `.json`） | 73,225 | 24.92 GB |
| `imgcache/` | 132,371 | 5.03 GB |
| `searchcache/` | 2,247 | 0.01 GB |
| `uploads/` | 1,462 | 0.43 GB |
| `fonts/` | 1,225 | 0.02 GB |
| `listed/` | 771 | 0.00 GB |

日ごとの生成数（観測から）は、共有が7,323件/日、`imgcache/` が16,546件/日。

### 月あたりのClass A（現状）

| 何 | 回数 |
| --- | --- |
| 定期の全件一覧（212回 × 144回/日） | 91.6万 |
| 起動時（`_seed_image_index` の132回 ＋ `_usage_loop` の212回。デプロイ10回/日と仮定） | 10.3万 |
| `PutObject`（共有7,323＋ `imgcache/` 16,546＋ 検索控え ≒ 2.5万/日） | 76.2万 |
| 合計 | **約178万** |

無料枠を78万回超え、$4.50 / 100万回で**月 $3.5**。`DeleteObject` は無料なので掃除は数えない。

## 何をするか

### 1. 数え直しの間隔を10分から3時間へ

`backend/storage.py` の `USAGE_CACHE_SEC` を600 → 10800。この定数は `_usage_loop` の `sleep` と
`usage_bytes()` のキャッシュ判定の両方が見ているので、1か所で足りる。
すぐ上の見出しコメント（`# ---- 使用量の集計（10分キャッシュ…） ----`）と `_usage_loop()` の
docstring（「以後10分ごと」）も同じ回に直す。数字が2か所に残ると次に読む人がずれる。

遅れが最大3時間になるが、`SHARE_BUDGET_GB` は本番で120 GB、実使用は30.41 GBなので上限には当たらない。
上限は暴走の歯止めであって正確な残量表示ではない、という今の位置づけは変えない。

### 2. 起動時の一覧を1周にまとめる

今は起動直後に2本の一覧が走り、`imgcache/` の分が二重になっている。

- `_seed_image_index()` … `imgcache/` を一覧（132回・約90秒）して `_IMG_INDEX` を作る
- `_usage_loop()` … 全件を一覧（212回・約132秒）して使用量を覚える

全件を1周する関数にまとめ、その1周で「`imgcache/` の索引」と「合計バイト数」を同時に作る。
起動あたり344回 → 212回。

`backend/storage.py` に、外で数えた値を覚えさせる口を足す。

```python
def set_usage(n: int) -> None:
    """外で数えた合計バイト数を覚える（起動時の一覧と相乗りするため）。"""
    global _usage
    with _usage_lock:
        _usage = (time.monotonic(), n)
```

`backend/main.py` 側:

- `_load_image_index()` を、接頭辞なしで1周して `(索引, 合計バイト数)` を返す形にする。
  索引に入れるのは今までどおり `imgcache/` で始まり、拡張子を除いた名前が20文字のキーだけ。
  合計バイト数は**全件**を足す（使用量の意味を変えない）。
- `_seed_image_index()` を `_seed_r2_index()` に改め、`st.is_remote` なら必ず走らせる。
  索引を作るのは `IMAGE_TO_R2` と公開URLが揃っているときだけ、使用量は常に `storage.set_usage()` に渡す。
- `_usage_loop()` は**先に眠ってから**数えるようにする（起動直後の1回は `_seed_r2_index()` が済ませている）。
  索引作りに失敗した場合は `set_usage()` が呼ばれないので、ループが最初の3時間後に拾い直す。

### 3. 索引の上限を上げる

`IMAGE_INDEX_MAX` の既定を200000 → 400000。`imgcache/` は132,371件で66% まで来ている。
1件150 B程度なので40万件で約60 MB。本番のRSSは211 MB、割当は2048 MBなので収まる。

### 4. `imgcache/` のヒット率を数える

`PutObject` は月76.2万回で、間引いたあとのClass Aの支配項になる。減らすべきかどうかは
**「置いた画像がもう一度要求される確率」**で決まるが、今は数えていない。

RenderはHobbyプランで、込みの帯域は月5 GBだけ。2026-09-20時点で143.33 GB使い、$20.85かかっている
（$0.15/GB）。キャッシュが無いと37 KBの画像1枚につき「配信元から取り直す」＋「利用者へ返す」で
2回ぶん＝74 KB＝ $0.0000106の帯域を食う。`PutObject` 1回は $0.0000045。
**つまり再要求の確率が42% を超えれば置くほうが得**。推計では43% でほぼ分岐点にあり、
測らずに減らすと帯域（Class Aの6倍の出費）を悪化させかねない。

`_note_src` / `_note_out` と同じ形で60秒ごとに1行出す。

```
[img] hit=N miss=M put=P stale=S
```

- `hit` … `_image_r2_redirect` が302を返せた回数
- `miss` … 返せずに本体を取りに行った回数
- `put` … `_image_to_r2` が成功した回数
- `stale` … `put` のうち、`_IMG_INDEX` に同じ鍵が**あったが期限切れだった**もの
  （＝新しい画像ではなく、期限切れによる取り直し。下の5の効果がここに出る）

`scripts/render_check.py` に1行足して要約に載せる。語やURLは出さない（件数だけ）。

### 5. `imgcache/` の保持と索引の期限をそろえて延ばす

今は索引とSQLiteが6日（`cache.R2_IMAGE_TTL`）、R2の掃除が7日（`r2-prune.yml` の
`--image-cache-hours 168`）。**6日を過ぎた画像は現物がR2にあるのに「無い」とみなされ、
配信元から取り直して同じ鍵に上書き `PutObject` している**。帯域2回ぶんとClass A 1回を捨てている。

掃除を14日（336時間）、索引とSQLiteを13日に延ばす。大小の関係（索引 < 掃除）は守る。

- ストレージ: 5.03 GB → 約10 GB。$0.015/GB・月なので **+$0.08/月**
- 取り直し: 期限切れによる分がおよそ半分になる。1回あたり帯域 $0.0000106＋Class A $0.0000045

**ストレージ（$0.015/GB・月）を帯域（$0.15/GB）と交換する取引なので、比が10倍こちらに有利**。
効果の実額は4の `stale` を見てから判断できるようにしておく（まず4を出し、数字を見て5を入れてもよい）。

`docs/ops.md` の「`imgcache/` だけは7日のまま」は、索引が6日で切れることを理由にしている。
両方そろえて延ばすので、その記述も同じ回に直す。

保持期間を**縮める**案は採らない。`imgcache/` はRenderの転送量を減らすためのものなので、
短くすると配信元からの取り直しが増え、帯域の出費がClass Aの節約を上回る。

## 直したあとの見込み

| 何 | 今 | 後 |
| --- | --- | --- |
| 定期の全件一覧 | 91.6万 | 5.1万 |
| 起動時 | 10.3万 | 6.4万 |
| `PutObject` | 76.2万 | 76.2万 |
| 合計 | 約178万（無料枠の178%） | **約87.6万（88%）** |

月 $3.5 → $0。余裕は12.4万回（約4,100回/日）。

`PutObject` は上の表では動かしていない（5の効果を数字が出るまで見込まないため）。
実際には5で期限切れの取り直しが減るぶん下がる。2026-09-16のような山（`imgcache/` が平均1.65万 →
4.27万件/日）が数日続けば無料枠を超えるが、超過50万回でも $2.25なので実害は小さい。

ストレージは30.41 − 10 = 20.41 GB × $0.015 = 月 $0.31。5で `imgcache/` が5 GB増えて +$0.08。
共有が30日ぶん溜まるとさらに伸びる。

### 出費の全体像（2026-09-20時点）

| 項目 | 月額 |
| --- | --- |
| 帯域143.33 GB（Hobbyの込みは5 GB） | $20.85 |
| サービス（Standardインスタンス） | $6.62 |
| Workspace | $4.71 |

**帯域がClass Aの6倍**で最大項。このspecはClass Aを $3.5 → $0にするもので、
帯域そのものは別のspec（`2026-09-20-index-split-design.md`）で扱う。

## 壊れ方と歯止め

- **一覧が失敗する**: 今までどおり握りつぶす。索引が無ければ配信元から取り直すだけで、壊れはしない。
  使用量が未取得なら `usage_cached()` は `None` を返し、`_check_budget` は通す（今と同じ）。
- **使用量の遅れ**: 最大3時間。上限120 GBに対し使用30 GBなので当たらない。
  当たりそうになったら間隔を縮めるか、保存のたびに加算する（今回は入れない）。
- **索引が上限に当たる**: 40万件を超えたぶんは索引に載らず、SQLiteも忘れていれば中継に落ちる。
  起動ログの件数で気付ける。
- **`_usage_loop` が先に眠る**ため、`_seed_r2_index()` が落ちると最初の3時間は使用量が `None` のまま。
  上限判定が通ってしまうが、歯止めなので許容する（今も起動直後の数分は同じ状態）。

## 確認のしかた

1. 手元で `PUBLIC_MODE=1` で起動し、起動ログに `[storage] imgcacheの索引: N件` と
   `[storage] 使用量X GB` が**1周で両方**出ることを見る。
2. `storage.usage_cached()` が起動直後から値を返すことを見る（今は `_usage_loop` の132秒後）。
3. `scripts/check_consistency.py` を回し、文書と食い違いが出ていないことを見る。
4. 本番へ出したあと `scripts/render_check.py --hours 2` を回し、
   `[storage] 使用量` の行が2時間に0〜1回になっていることを見る（今は12回）。
5. 同じ点検で `[img] hit=… miss=… put=… stale=…` が出ていることを見る。
   `hit / (hit + miss)` が42% を超えていれば、`imgcache/` に置き続ける判断が正しいと確かめられる。
   `stale` が `put` の大きな割合を占めるなら、5（期限を延ばす）の効果が大きいと分かる。
