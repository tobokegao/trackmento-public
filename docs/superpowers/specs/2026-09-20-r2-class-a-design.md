# R2 の Class A 操作を減らす（全件一覧の間引きと起動時の相乗り）

2026-09-20

## 何を直すか

R2 の Class A 操作が無料枠（100 万回/月）を超えている。原因の大半は、共有の容量上限を測るためだけに
10 分ごとに回している**バケット全件の一覧**。

### 実測（2026-09-20）

バケットは 211,301 件・30.41 GB。全件の一覧に 132 秒、Class A で 212 回かかる。

| 内訳 | 件数 | 容量 |
| --- | --- | --- |
| 共有（バケット直下の `<id>.jpg` / `-og.jpg` / `.json`） | 73,225 | 24.92 GB |
| `imgcache/` | 132,371 | 5.03 GB |
| `searchcache/` | 2,247 | 0.01 GB |
| `uploads/` | 1,462 | 0.43 GB |
| `fonts/` | 1,225 | 0.02 GB |
| `listed/` | 771 | 0.00 GB |

日ごとの生成数（観測から）は、共有が 7,323 件/日、`imgcache/` が 16,546 件/日。

### 月あたりの Class A（現状）

| 何 | 回数 |
| --- | --- |
| 定期の全件一覧（212 回 × 144 回/日） | 91.6 万 |
| 起動時（`_seed_image_index` の 132 回 ＋ `_usage_loop` の 212 回。デプロイ 10 回/日と仮定） | 10.3 万 |
| `PutObject`（共有 7,323 ＋ `imgcache/` 16,546 ＋ 検索控え ≒ 2.5 万/日） | 76.2 万 |
| 合計 | **約 178 万** |

無料枠を 78 万回超え、$4.50 / 100 万回で**月 $3.5**。`DeleteObject` は無料なので掃除は数えない。

## 何をするか

### 1. 数え直しの間隔を 10 分から 3 時間へ

`backend/storage.py` の `USAGE_CACHE_SEC` を 600 → 10800。この定数は `_usage_loop` の `sleep` と
`usage_bytes()` のキャッシュ判定の両方が見ているので、1 か所で足りる。
すぐ上の見出しコメント（`# ---- 使用量の集計（10 分キャッシュ…） ----`）と `_usage_loop()` の
docstring（「以後 10 分ごと」）も同じ回に直す。数字が 2 か所に残ると次に読む人がずれる。

遅れが最大 3 時間になるが、`SHARE_BUDGET_GB` は本番で 120 GB、実使用は 30.41 GB なので上限には当たらない。
上限は暴走の歯止めであって正確な残量表示ではない、という今の位置づけは変えない。

### 2. 起動時の一覧を 1 周にまとめる

今は起動直後に 2 本の一覧が走り、`imgcache/` の分が二重になっている。

- `_seed_image_index()` … `imgcache/` を一覧（132 回・約 90 秒）して `_IMG_INDEX` を作る
- `_usage_loop()` … 全件を一覧（212 回・約 132 秒）して使用量を覚える

全件を 1 周する関数にまとめ、その 1 周で「`imgcache/` の索引」と「合計バイト数」を同時に作る。
起動あたり 344 回 → 212 回。

`backend/storage.py` に、外で数えた値を覚えさせる口を足す。

```python
def set_usage(n: int) -> None:
    """外で数えた合計バイト数を覚える（起動時の一覧と相乗りするため）。"""
    global _usage
    with _usage_lock:
        _usage = (time.monotonic(), n)
```

`backend/main.py` 側:

- `_load_image_index()` を、接頭辞なしで 1 周して `(索引, 合計バイト数)` を返す形にする。
  索引に入れるのは今までどおり `imgcache/` で始まり、拡張子を除いた名前が 20 文字のキーだけ。
  合計バイト数は**全件**を足す（使用量の意味を変えない）。
- `_seed_image_index()` を `_seed_r2_index()` に改め、`st.is_remote` なら必ず走らせる。
  索引を作るのは `IMAGE_TO_R2` と公開 URL が揃っているときだけ、使用量は常に `storage.set_usage()` に渡す。
- `_usage_loop()` は**先に眠ってから**数えるようにする（起動直後の 1 回は `_seed_r2_index()` が済ませている）。
  索引作りに失敗した場合は `set_usage()` が呼ばれないので、ループが最初の 3 時間後に拾い直す。

### 3. 索引の上限を上げる

`IMAGE_INDEX_MAX` の既定を 200000 → 400000。`imgcache/` は 132,371 件で 66% まで来ている。
1 件 150 B 程度なので 40 万件で約 60 MB。本番の RSS は 211 MB、割当は 2048 MB なので収まる。

### 4. `imgcache/` のヒット率を数える

`PutObject` は月 76.2 万回で、間引いたあとの Class A の支配項になる。減らすべきかどうかは
**「置いた画像がもう一度要求される確率」**で決まるが、今は数えていない。

Render は Hobby プランで、込みの帯域は月 5 GB だけ。2026-09-20 時点で 143.33 GB 使い、$20.85 かかっている
（$0.15/GB）。キャッシュが無いと 37 KB の画像 1 枚につき「配信元から取り直す」＋「利用者へ返す」で
2 回ぶん＝ 74 KB＝ $0.0000106 の帯域を食う。`PutObject` 1 回は $0.0000045。
**つまり再要求の確率が 42% を超えれば置くほうが得**。推計では 43% でほぼ分岐点にあり、
測らずに減らすと帯域（Class A の 6 倍の出費）を悪化させかねない。

`_note_src` / `_note_out` と同じ形で 60 秒ごとに 1 行出す。

```
[img] hit=N miss=M put=P stale=S
```

- `hit` … `_image_r2_redirect` が 302 を返せた回数
- `miss` … 返せずに本体を取りに行った回数
- `put` … `_image_to_r2` が成功した回数
- `stale` … `put` のうち、`_IMG_INDEX` に同じ鍵が**あったが期限切れだった**もの
  （＝新しい画像ではなく、期限切れによる取り直し。下の 5 の効果がここに出る）

`scripts/render_check.py` に 1 行足して要約に載せる。語や URL は出さない（件数だけ）。

### 5. `imgcache/` の保持と索引の期限をそろえて延ばす

今は索引と SQLite が 6 日（`cache.R2_IMAGE_TTL`）、R2 の掃除が 7 日（`r2-prune.yml` の
`--image-cache-hours 168`）。**6 日を過ぎた画像は現物が R2 にあるのに「無い」とみなされ、
配信元から取り直して同じ鍵に上書き `PutObject` している**。帯域 2 回ぶんと Class A 1 回を捨てている。

掃除を 14 日（336 時間）、索引と SQLite を 13 日に延ばす。大小の関係（索引 < 掃除）は守る。

- ストレージ: 5.03 GB → 約 10 GB。$0.015/GB・月なので **+$0.08/月**
- 取り直し: 期限切れによる分がおよそ半分になる。1 回あたり帯域 $0.0000106 ＋ Class A $0.0000045

**ストレージ（$0.015/GB・月）を帯域（$0.15/GB）と交換する取引なので、比が 10 倍こちらに有利**。
効果の実額は 4 の `stale` を見てから判断できるようにしておく（まず 4 を出し、数字を見て 5 を入れてもよい）。

`docs/ops.md` の「`imgcache/` だけは 7 日のまま」は、索引が 6 日で切れることを理由にしている。
両方そろえて延ばすので、その記述も同じ回に直す。

保持期間を**縮める**案は採らない。`imgcache/` は Render の転送量を減らすためのものなので、
短くすると配信元からの取り直しが増え、帯域の出費が Class A の節約を上回る。

## 直したあとの見込み

| 何 | 今 | 後 |
| --- | --- | --- |
| 定期の全件一覧 | 91.6 万 | 5.1 万 |
| 起動時 | 10.3 万 | 6.4 万 |
| `PutObject` | 76.2 万 | 76.2 万 |
| 合計 | 約 178 万（無料枠の 178%） | **約 87.6 万（88%）** |

月 $3.5 → $0。余裕は 12.4 万回（約 4,100 回/日）。

`PutObject` は上の表では動かしていない（5 の効果を数字が出るまで見込まないため）。
実際には 5 で期限切れの取り直しが減るぶん下がる。2026-09-16 のような山（`imgcache/` が平均 1.65 万 →
4.27 万件/日）が数日続けば無料枠を超えるが、超過 50 万回でも $2.25 なので実害は小さい。

ストレージは 30.41 − 10 = 20.41 GB × $0.015 = 月 $0.31。5 で `imgcache/` が 5 GB 増えて +$0.08。
共有が 30 日ぶん溜まるとさらに伸びる。

### 出費の全体像（2026-09-20 時点）

| 項目 | 月額 |
| --- | --- |
| 帯域 143.33 GB（Hobby の込みは 5 GB） | $20.85 |
| サービス（Standard インスタンス） | $6.62 |
| Workspace | $4.71 |
| R2 Class A（超過 78 万回） | $3.5 |
| R2 ストレージ | $0.31 |
| 9 月の見込み合計 | **$40.94** |

**帯域が Class A の 6 倍**で最大項。この spec は Class A を $3.5 → $0 にするもので、
帯域そのものは別の spec（`2026-09-20-index-split-design.md`）で扱う。

## 壊れ方と歯止め

- **一覧が失敗する**: 今までどおり握りつぶす。索引が無ければ配信元から取り直すだけで、壊れはしない。
  使用量が未取得なら `usage_cached()` は `None` を返し、`_check_budget` は通す（今と同じ）。
- **使用量の遅れ**: 最大 3 時間。上限 120 GB に対し使用 30 GB なので当たらない。
  当たりそうになったら間隔を縮めるか、保存のたびに加算する（今回は入れない）。
- **索引が上限に当たる**: 40 万件を超えたぶんは索引に載らず、SQLite も忘れていれば中継に落ちる。
  起動ログの件数で気付ける。
- **`_usage_loop` が先に眠る**ため、`_seed_r2_index()` が落ちると最初の 3 時間は使用量が `None` のまま。
  上限判定が通ってしまうが、歯止めなので許容する（今も起動直後の数分は同じ状態）。

## 確認のしかた

1. 手元で `PUBLIC_MODE=1` で起動し、起動ログに `[storage] imgcache の索引: N 件` と
   `[storage] 使用量 X GB` が**1 周で両方**出ることを見る。
2. `storage.usage_cached()` が起動直後から値を返すことを見る（今は `_usage_loop` の 132 秒後）。
3. `scripts/check_consistency.py` を回し、文書と食い違いが出ていないことを見る。
4. 本番へ出したあと `scripts/render_check.py --hours 2` を回し、
   `[storage] 使用量` の行が 2 時間に 0〜1 回になっていることを見る（今は 12 回）。
5. 同じ点検で `[img] hit=… miss=… put=… stale=…` が出ていることを見る。
   `hit / (hit + miss)` が 42% を超えていれば、`imgcache/` に置き続ける判断が正しいと確かめられる。
   `stale` が `put` の大きな割合を占めるなら、5（期限を延ばす）の効果が大きいと分かる。
