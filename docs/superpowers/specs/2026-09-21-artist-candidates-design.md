# アーティスト名の候補を出す（転載動画の元の投稿者を含む）

2026-09-21

前提: [曲名・アーティスト名の蛇足を外す](2026-09-21-trim-names-design.md)。
あちらは**規則だけで確実に直せるもの**を扱う。こちらは**確実には決められないもの**を、
利用者に選んでもらうための仕掛け。

## 何を直すか

YouTube から取り込んだ曲のアーティスト名は、oEmbed の `author_name`（チャンネル名）そのまま
（`backend/sources/video.py`）。チャンネル名がアーティスト名でないことがある。

### 1. チャンネル名が宣伝文・レーベル名

規則で直せるものは spec 1 の A1・A2・G が拾う。拾えないものが残る。

```
題    : 童遊（めらみぽっぷ＆いお ver.）
作者欄: RD-Sounds / 凋叶棕 Official        ← Official が末尾でないので R2 が効かない
```

### 2. 転載

動画の投稿者が、曲を作った人とは限らない。

```
題    : 【ニコカラ】物凄い狂っとるフランちゃんが物凄いうた（OnVo）【字幕大】
作者欄: qfeuille3_v2 🥐⚓                   ← 転載した人
正しい: Pangelino（ニコニコ動画 sm12305503 の投稿者）
```

**転載の向きは 4 通りある**。「ニコニコから取ったものは投稿者が正しい」とは言えない。

| 向き | この設計で拾えるか |
| --- | --- |
| ニコニコ → YouTube | 概要欄に書いてあれば拾える。無ければニコニコの検索で探せる |
| YouTube → YouTube | 概要欄に書いてあれば拾える |
| YouTube → ニコニコ | ニコニコの検索で同じ題の古い投稿として拾える |
| ニコニコ → ニコニコ | 同上 |

## 何をするか

**候補を出して利用者が選ぶ**。自動では差し替えない。間違った名前を黙って載せるのが
いちばん悪い（消すだけの刈り込みと違い、差し替えは誤りを作る）。

手がかりは 3 つ。確かな順に並べる。

### 手がかり 1: YouTube の概要欄（取り込むときに取る）

**YouTube の取得を oEmbed から Data API の `videos.list` に差し替える**。
`YOUTUBE_API_KEY` は再生リストの取得（`playlist.py` の `playlistItems.list`）で既に使っている。

```
https://www.googleapis.com/youtube/v3/videos
  part   = snippet
  id     = <動画 ID を 50 件までまとめて>
  fields = items(id,snippet(title,channelTitle,description,publishedAt))
```

概要欄から元動画を抜く。**手がかりの語**（下）が同じ行か 1 つ前の行にあるときだけ、
その行の URL を元とみなす。

```
転載|本家|原曲|元動画|元ネタ|再\s*up|re-?up(?:load)?|mirror|reprint|
source|original|出典|引用元|より転載|さんの動画
```

URL は `nicovideo.jp/watch/(sm|nm|so)\d+`・`nico.ms/…` と
`youtu.be/…`・`youtube.com/watch?v=…`（11 文字）。自分自身の ID は除く。

元がニコニコなら既存の `NICO_THUMBINFO`（`getthumbinfo`）で投稿者名に、
元が YouTube なら同じ `videos.list` で `channelTitle` に変換する。

#### 実測（2026-09-21、みんなの並び 41 件の YouTube 113 曲）

| | |
| --- | --- |
| 元動画が見つかった | **1 件 / 113 件（1%）** |
| 誤検出 | **0 件** |

概要欄にニコニコの URL があるのは 4 件だが、うち 3 件は**転載ではない**
（`暁Records` が自分のニコニコ版へリンク、`maritumix` が自分の別動画へ誘導）。
手がかりの語で絞ることで、この 3 件を正しく外せている。

**転載は珍しい。だが当たったときは確実**。費用がほぼゼロ（下）なので取りに行く価値はある。

#### 概要欄の「作者らしい名前」は採らない

`Karaoke by …`・`作曲: …`・`原作: …` のような行から名前を拾う案も試したが、
113 件中 20 件で取れた名前の大半が**原曲の作者**（`ZUN（上海アリス幻樂団）`）や
**原作名**（`東方妖々夢`・`東方永夜抄`）で、アーティスト名としては誤り。見分けがつかないので採らない。

### 手がかり 2: 題の中の名前（すぐ出る）

題の `/` 区切りの部分と `【】` の中身から、spec 1 の刈り込みを通したもの。
問い合わせが要らないので、編集パネルを開いた時点で出せる。

マスのアーティスト名に**チャンネル臭**があるときだけ出す。

- spec 1 の A2 の宣伝の文句を含む
- `公式チャンネル` `Official` `Channel` `チャンネル` を含む

絞らないと、`【魂音泉】`（サークル名）や `【ハルトマンの妖怪少女】`（原曲名）が
全マスで候補に出て鬱陶しい。100 曲の並びで実際にそうなった。

### 手がかり 3: ニコニコ動画の古い投稿（押したときだけ引く）

概要欄に何も書いていない転載のための最後の手段。
編集パネルの「元の投稿を探す」を押したときだけ引く。**自動では引かない**。

**マスの出どころで絞らない**。ニコニコから取ったマスも対象（ニコニコ内での転載があるため）。
ニコニコのマスでは、そのマス自身の動画より**古い一致があるときだけ**候補を出す。

1. **スナップショット検索 API**

   ```
   https://snapshot.search.nicovideo.jp/api/v2/snapshot/video/contents/search
     q       = 刈り込みを通した題
     targets = title
     fields  = contentId,title,userId,startTime,viewCounter
     _sort   = -viewCounter
     _limit  = 10
     _context= trackmento
   ```

2. **一致度で絞る**。正規化した題どうしの**共通接頭辞の長さ ÷ 長いほうの長さ**
3. 絞ったものを**投稿日の古い順**に並べ替える。元の投稿がいちばん古い見込みが高い
4. 上位 **3 件**だけ `getthumbinfo` で投稿者名（`user_nickname`）に変換
5. 投稿者名・動画 ID・投稿日を候補として出す

古い順が元とは限らない（元が消えて再投稿されたもの、権利者が後から上げ直したものがある）ので、
**候補として出すだけ**。

#### 実測（2026-09-21）

`物凄い狂っとるフランちゃんが物凄いうた` で `totalCount` 65 件。

| 動画 | 題 | 一致 |
| --- | --- | --- |
| `sm12305503` | `【ニコカラ】物凄い狂っとるフランちゃんが物凄いうた(OnVo)【ななひら】` | 共通部分が YouTube 題の全長 → **1 位**。投稿者 `Pangelino`（正解） |
| `sm12298171` | `【東方ニコカラ】物凄い狂っとるフランちゃんが物凄いうた【^p^】(on vocal)` | `(OnVo)` と `(on vocal)` で分岐 → 2 位 |
| `sm12085793` | `ニコ静ツアー - 物凄い狂っとるフランちゃんが物凄いうた` | 頭が違う → 下位（再生数は最多の 121 万） |

**再生数順のままだと別の動画が 1 位になる**。並べ替えの鍵は一致度と投稿日。

## 費用（実測から）

### YouTube Data API

| | |
| --- | --- |
| クォータ | `videos.list` は **1 unit / 回**。`id` を **50 件までまとめられる** |
| 日あたり | YouTube 由来は全体の **23%**（41 並び 882 曲の実測）。画像取得が 16,546 件/日（`docs/ops.md`）なので、多く見て 3,800 曲/日 |
| 消費 | 3,800 ÷ 50 = **76 units/日**。無料枠 10,000 units/日の **0.8%** |

`playlistItems.list` と同じ枠を食うが、余裕は十分。**クォータを超えたら oEmbed に倒す**
（再生リストの取得を巻き添えにしない）。

### 転送量

`fields` で絞ると 1 件 **1.0 KB**（113 件の実測で 110.5 KB）。3,800 曲で **3.8 MB/日**。
絞らないと 5.7 KB/件なので、`fields` は必ず付ける。

これは Render が**受信**する分。Render の課金は送信が対象なので乗らないはずだが、
念のため小さく保つ。

### 保存するデータ

**概要欄は保存しない**。検出結果だけ持つ。

```
origin: {kind: "nicovideo", id: "sm12305503", artist: "Pangelino"}   約 60 bytes
```

- grid JSON: 1 並びあたり **+0.3 KB**（21.5 曲 × 23% × 60B）
- 共有 JSON: 7,323 件/日 × 0.3 KB = 2.2 MB/日 → 30 日で **65 MB**。R2 の 28.5 GB に対して **+0.2%**

### ニコニコのスナップショット検索

無料。押したときだけ引くので日常の負荷はゼロ。

## 画面

編集パネル（選択中のマス）に出す。

```
07 選択中のマス
曲名   [ 物凄い狂っとるフランちゃんが物凄いうた（OnVo）  ]
アーティスト名 [ qfeuille3_v2 🥐⚓                      ]

⚠ ニコニコ動画からの転載です（sm12305503）
     [ Pangelino にする ]

ニコニコ動画で古い投稿を探す  [ 探す ]
```

- **⚠ の行**は概要欄から元が見つかったときだけ（取り込み済みなので待ち時間なし）
- **チャンネル臭**があるときは、題の中の名前も候補に並べる
- **「ニコニコ動画で古い投稿を探す」はどのマスにも出す**
- 候補を押すとアーティスト名の欄が入れ替わる（データを書き換える。取り消しは 1 回ぶん持つ）

一括では出さない。100 マスぶんの候補を並べても選べない。
並べ替えの下に「アーティスト名を確かめたいマス: 3 件」とだけ出し、押すとそのマスを順に選ぶ
（数えるのは転載が見つかったマスとチャンネル臭のあるマス）。

## どこを直すか

| ファイル | 何を |
| --- | --- |
| `backend/sources/video.py` | `fetch_youtube` を `videos.list` に差し替え（鍵が無い・クォータ超過なら oEmbed に倒す）。概要欄から元動画を抜く |
| `backend/sources/nicosearch.py`（新規） | スナップショット検索 API と一致度の並べ替え |
| `backend/main.py` | `/artist-candidates?title=…` を足す |
| `backend/grids.py` | `Cell` に `origin` を足す |
| `backend/cache.py` | 結果を覚える（`SEARCH_TTL_BY_SOURCE` に `nicosearch` を足す。7 日） |
| `backend/searchcache.py` | R2 の控えにも入れる（`cache.sqlite3` はデプロイで消えるため） |
| `frontend/index.html` | 編集パネルの候補欄、チャンネル臭の判定（spec 1 の `trimName()` と同じファイル） |
| `docs/services-terms.md` | ニコニコのスナップショット検索 API の規約・上限・`_context` の決まり。YouTube Data API の使い方が増えたこと |
| `docs/sources.md` | 候補の出どころとして書く |
| `docs/env.md` | `YOUTUBE_API_KEY` が単体の動画にも効くようになったこと（今は「再生リストだけ」と書いてある） |

## 守ること

- **1 秒に 1 リクエストまで**（ニコニコのスナップショット検索 API の目安）
- `_context` に `trackmento` を入れる（API の決まり）
- **検索語を恒常的に記録しない**。`searchcache.py` の既存の決まりと同じで、鍵は HMAC にして
  中身に題を入れない（プライバシーポリシーとの両立）
- **Data API のクォータが尽きても落ちない**。`videos.list` が 403（quotaExceeded）を返したら
  oEmbed に倒す。再生リストの取得を巻き添えにしない

## やらないこと

- 自動での差し替え（規則で確実に決まるものは spec 1 の A1・A2・G が受け持つ）
- 概要欄の「作者らしい名前」を拾うこと（原曲の作者・原作名を拾ってしまう。上の実測）
- 概要欄そのものを保存すること（データが重くなる。検出結果だけ持つ）
- otoDB・VocaDB への問い合わせ（東方アレンジ・ニコカラはどちらにも入っていないことが多い）
- 一括での候補提示（100 マスぶんは選べない）
